# Human and Agent story campaign

Start from the person's intended activity in their existing tools, not a product

Required: selected story and source basis, actual permitted World/material,

do safe preparation and native tests; never claim the rendered interface was used.
Personal-source adoption, spending and shared/public effects need their own grants.

## Procedure

1. **Bind a useful first batch.** Recover the real root/meta-Project or child
   scope and chosen installation/composition. Start with ordinary existing-tool
   work, governance/context and knowledge, then expand along actual readiness.
   Do not require every product or a finished Factory before testing a smaller
   World. Missing required code is owner implementation work, not local proof.
2. **Prepare both sides of each activity.** The human task stays plain language.
   In the existing UX `extensions.participation`, bind roles, triggering situation,
   determining context/authority/capability conditions, exact practice and public
   operations, observable results, preserved invariants and recovery/continuation.
   Candidate family dependencies are narrowed per step; never load them all.
3. **Separate test roles.** The worker receives the normal task and permitted
   context, not the verifier's answer or a hidden setup helper. The orchestrator
   prepares/monitors, a computer-use actor uses real visible controls, an independent
   verifier checks actual effects, and a repair worker fixes the correct owner.
   Test roles do not create permanent user Agents or confer extra permissions.
4. **Allocate safely.** Parallelise disjoint test roots, worktrees, conversations,
   ports, services and budgets. One actor owns a desktop's input at a time.
   Serialize global configuration, active suite and shared source changes.
   Preserve the person's dirty work and private material; use approved specimens
   for denied writes, interrupted installation and other consequential failures.
5. **Exercise the intended route.** A quiet-use story starts in the normal harness;
   a UI story uses rendered controls; an Agent-native story uses public operations.
   Record actual task/context/practice, dispatch, effects/readback and source/cut.
   An API success can diagnose a broken control, not substitute for using it.
6. **Diagnose the earliest failed step.** Check orientation, received/permitted
   context, description-based practice discovery, actual loading, tool/authority,
   dispatch, material effect, source freshness, UI projection and test expectation.
   Do not assume disobedience before establishing what the worker actually knew
   and could do. Do not retry an uncertain consequential effect without reconciliation.
7. **Repair and independently rerun.** Freeze the first failure and any assistance.
   Fix native invariants at their owner; repair descriptions/practice where those
   caused the problem. Retain existing active integration ownership. Add a regression,
   record any changed source/install basis, then rerun the whole affected activity
   with a fresh uncoached participant. Assisted completion remains labelled assisted.
8. **Report and continue.** Explain what the person can now do, what changed, what
   remains and any genuine decision needed. Keep exact evidence behind that account.
   One orchestrator owns the next batch and owner repairs; do not route the person
   through A–E chats. Archive through the native retention path with pending work intact.
