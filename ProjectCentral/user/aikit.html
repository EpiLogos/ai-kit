#0 · Why?

Why? Make the available world usable

Agentic work draws on tools, Skills, knowledge, models and working environments that come from many places. A person needs these resources to become a coherent working context without rebuilding their setup around each Agent. AIKit makes the relevant part of that world discoverable, explainable and usable for the work at hand.

What? The composition and disclosure toolkit

AIKit is a Rust CLI, TUI and shared application toolkit for discovering agent resources, selecting them for a Project or task, and projecting the resulting configuration into supported harnesses. It also provides knowledge search and retrieval, semantic Wiki navigation, runtime composition and session integration. Its concrete product is an inspectable answer to what this actor can use and ask about here.

#0Why?

Make the available world usable

0/1 · Return to the seedExpanded account · review draft
vision

A capable environment should be understandable

A person may already have several model subscriptions, repositories, command-line tools and collections of Skills. Each new harness can introduce another configuration directory and another account of what is installed. The useful question is simple: what can I use for this work, and how do I get to it?

AIKit aims to make that question answerable from the current Project. Someone entering a repository should discover the relevant capabilities and sources, inspect the applicable choices, and understand the next operation. They should be able to keep a broad collection without repeatedly loading every instruction into every conversation.

The experience matters for an Agent as well. Before acting, it needs to understand where it is, what it can ask about and which operations are available. A compact orientation can establish this starting point while preserving routes to deeper material. [[cap.aikit.context-resolution|Context resolution]] and [[cap.aikit.source-horizon|source horizons]] provide the functional basis.

This seed is recovered from the product thesis and development programme. It is an Agent-written candidate for human review. It develops the supplied Central convention while preserving AIKit’s own product purpose.

docs/v2/01-PRODUCT-AND-OWNERSHIP.md
design commitment

Keep the person’s existing world in view

Existing tools are the starting material. A useful discovery pass can show foreign Skills and their provenance before a user decides whether to manage them through AIKit. Adoption should preserve the original material, explain the proposed change and provide an intelligible route back.

The same continuity applies to Project source. A design account, ordinary note and repository file can remain in their own locations. AIKit establishes references and retrieval routes over them. The person can then develop a coherent practice without first converting every file into a special document type.

This reduces repeated setup work and preserves choice. A new harness can receive a suitable projection of an existing selection. A new model can be evaluated against present requirements. The durable purpose remains available even when its current provider changes. [[cap.aikit.discovery|Discovery]], [[cap.aikit.adoption|adoption]] and [[cap.aikit.projection|projection]] serve this continuity.

The desired opening experience gives enough information to proceed: Project identity, current focus, relevant capability names, source destinations and any material limitations. Deeper instructions become useful when a person or Agent chooses a particular operation.

This is a relationship between attention and availability. A reference can be known before its payload is read. A retrieved source can inform one decision without becoming permanent standing context. Keeping these steps explicit makes it possible to investigate a large Project through a small sequence of deliberate questions.

#1What?

The composition and disclosure toolkit

0/1 · Return to the seedExpanded account · review draft
surface discovery

The CLI, TUI and shared services

AIKit is a toolkit for composing the resources available to an Agent and disclosing the knowledge relevant to its work. The CLI makes operations scriptable. The TUI provides search, inspection and staged changes. Shared application services carry the same resolution and knowledge meanings across these surfaces.

The resource field includes Skills, Actions, models, ContextSources and runtime Components. A Profile collects operational choices. A Project binding locates those choices in a particular repository. A generation records a resolved view that an adapter can expose to a target harness.

The working sequence is discover, select, inspect and apply. A user can register a source, search its resources, choose a SkillSet, inspect the effective environment and publish the relevant projection. [[cap.aikit.resource-index|Resource indexing]], [[cap.aikit.profiles|Profiles]] and [[cap.aikit.generation|generations]] connect these operations.

The native source contains both established CLI behaviour and newer V2 application services. This account describes their intended relationship and links each capability to its implementation scope. It does not infer full installed or physical acceptance from the breadth of the source tree.

docs/v2/01-PRODUCT-AND-OWNERSHIP.md
surface discovery

Knowledge that can be asked for

A ContextSource is an addressable source of information. AIKit can establish its identity, eligibility and retrieval route before reading its full content. The source may be a local Project document, a SourcePool item, a semantic Wiki or a code intelligence provider.

The Wiki represents semantic nodes, spaces, relationships and contextual readings. A SourcePool widens the evidential horizon. A code provider offers structural relationships in the implementation. ProjectMap connects these lenses through explicit references so a reader can move from a concept to its source or implementation.

[[cap.aikit.knowledge-navigation|Knowledge navigation]] offers search and bounded expansion. [[cap.aikit.wiki-write|Wiki maintenance]] gives Agents an explicit way to record and revise navigational structure. [[cap.aikit.authored-relations|Source relation compilation]] preserves links found in supported authored text together with their original source and location.

docs/v2/02-RESOLUTION-AND-CONTEXT-COGNITION.md
surface discovery

Reusable practice and working bodies

A Skill contains reusable organised practice. A Method situates practice around a purpose, inputs, operations and an expected result. SkillSets and Profiles help select this material for the current work. The result should make a familiar task easier to perform without replacing the task’s particular intention.

Runtime composition addresses the body through which the work happens. Harnesses and Components declare requirements and contributions. SessionSpace records the relation between an Agent session and the surfaces through which it is encountered. Providers connect those semantics to actual terminal sessions or other working environments.

[[cap.aikit.methods|Methods]], [[cap.aikit.composition|runtime composition]] and [[cap.aikit.sessions|session integration]] therefore meet different needs. The first organises practice, the second selects a workable body, and the third preserves the relation to an ongoing encounter. [[cap.aikit.routines|Routines]] add a proof and authority basis for repeatable Method execution.

#2How?

Resolve first, disclose as needed

0/1 · Return to the seedExpanded account · review draft
implementation guide

Enter a Project with a useful environment

Begin from the repository where the work belongs. Inspect its Project binding and effective configuration. Search the resource catalogue for the capability needed by the task, then inspect the source, requirements and explanation before choosing it.

A project-specific choice should leave unrelated work understandable. A shared baseline can supply common Skills while a local overlay adds the Project’s particular instructions. An invocation-level refinement can serve one task without turning a temporary need into a permanent global default.

After reviewing the resolved selection, apply the projection through AIKit. The useful result is a reproducible filesystem view for the target client and an explanation of how that view arose. An already-running harness may cache its catalogue; check its reported state or begin a fresh task when loading must be established.

This journey uses [[cap.aikit.context-resolution|resolution]], [[cap.aikit.profiles|scoped Profiles]], [[cap.aikit.generation|generation publication]] and [[cap.aikit.activation|activation evidence]]. Success means the intended capability is available in the intended context and its operative use can be distinguished from the files that expose it.

AGENTS.md
protocol method

Follow a question back to exact source

Enter the Project’s knowledge view with a question. Search for the concept or use an exact reference when one is known. Inspect the result’s provider, source revision and relationships before expanding the surrounding neighbourhood.

A useful path may begin at the product overview, follow a capability into a design unit, then retrieve a ticket correction or a code location. The Wiki supplies navigational relationships. Exact source supplies the passage on which a claim depends. Bounded expansion keeps a local investigation manageable.

When a result is absent, ambiguous or unavailable, retain that condition in the answer. It tells the next actor what remains to be recovered. A loose note can participate as source without being promoted into a product contract, and a formal HTML account retains the standing of the material it actually contains.

This journey combines [[cap.aikit.projectcentral|ProjectCentral discovery]], [[cap.aikit.source-horizon|explicit retrieval]], [[cap.aikit.knowledge-navigation|navigation]] and [[cap.aikit.reflection|semantic-to-code reflection]]. The return should name the source and revision that justify the conclusion.

registry/capsules/skill/aikit/knowledge-navigation/payload/SKILL.md
protocol method

Turn useful understanding into navigable knowledge

An Agent may discover that several documents describe one capability in different terms. Recover the relevant passages, identify the shared subject and record the relationship with source provenance. Keep unresolved differences available for review.

Wiki writes name the destination file and the intended object change. The native pipeline parses the existing document, mutates in memory, validates the resulting whole and renders the accepted result for atomic persistence. A refusal leaves the file unchanged. This makes small, inspectable maintenance possible.

For supported Markdown, source links and OKF properties can contribute relation evidence. Wiki staging additionally requires the source’s explicit authored alignment. A missing alignment is a visible request for determination. It should never be guessed from a filename or inferred merely because the source is useful.

[[cap.aikit.wiki-write|Explicit Wiki mutation]], [[cap.aikit.authored-relations|relation compilation]] and [[cap.aikit.living-knowledge|change impact]] let the navigation develop alongside real source. When a human-owned statement needs revision, return a proposal to its owner and preserve the original basis until that revision is accepted.

implementation guide

Change the working setup with a visible result

A person composing a runtime begins with the work’s requirements: the necessary capabilities, supported model, useful surfaces and execution conditions. Inspect candidate Components and provider bindings, then review whether the requirements are satisfied.

A preview should explain what the proposed composition contributes and what remains unavailable. A successful configuration write establishes the intended material view. Provider observations and activation receipts establish what the target actually made effective.

For portable terminal work, declare the session topology, compare it with the present backend and reconcile the intended change within owned resources. Existing unrelated panes remain outside the declared ownership boundary. A later inspection should make the resulting topology and any difference clear.

The journey connects [[cap.aikit.composition|composition]], [[cap.aikit.models|model fit]], [[cap.aikit.sessions|sessions]] and [[cap.aikit.procedures|reviewable Procedures]]. Its outcome is a working arrangement whose changes and limitations the user can inspect.

#3Who / Whereby?

One environment, several ways to encounter it

0/1 · Return to the seedExpanded account · review draft
architecture contract

References connect resources to their owners

A resource needs a stable reference, an owner, a revision and a locator. The reference supports continuity while the locator tells the current provider where to retrieve or operate it. Provenance connects the current reading to its source.

An application Action keeps its native operation and identity when AIKit exposes it as a capability. A Project keeps its source ownership when it enters a knowledge horizon. A model or harness keeps its provider-specific implementation while contributing to a common resolution.

These relationships let several surfaces show the same operation without inventing separate handlers or competing truth. The CLI, TUI and Agent-facing reading should agree about the selected resource and its basis, even when they display it differently.

The shared [[source:covenant|O:I primitive relations]] ground these names. AIKit develops the operational selection and disclosure relations; Central keeps durable authored ground, Actuation supplies authority and agency, Factory owns development and Workcell supplies material execution.

docs/v2/01-PRODUCT-AND-OWNERSHIP.md
architecture contract

Make every effective choice explainable

Resolution combines declarations with present conditions. Scope determines which choice applies. Trust, policy, compatibility and requirements determine whether the candidate is eligible. Preferences choose among eligible possibilities.

An explanation should show the origin of a selection, the source revision, any inherited constraints and the reason an alternative was excluded. This is practical debugging information when a Skill appears in one Project and disappears in another.

Generated state should be replaceable from the underlying declarations and sources. A generation provides a complete view whose publication can be checked against the expected prior basis. External mutation needs an explicit Procedure with an inspectable effect and reversal path.

[[cap.aikit.explain|Explain and History]] make that causal account available. [[cap.aikit.familiarity|Familiarity]] may improve access among eligible results while exact addressing and authored preference retain their own meanings. Usage frequency is useful navigation evidence; it cannot establish authority.

docs/v2/02-RESOLUTION-AND-CONTEXT-COGNITION.md
architecture contract

Read source faithfully across different forms

The source contract begins with identity and permission. ProjectCentral discovery uses small manifests and filesystem metadata to establish what can be encountered. Explicit reads obtain payloads. A recursive .no-agent-retrieval boundary excludes the covered subtree before disclosure.

Central’s recognised source relations carry provenance, truth standing, roles and treatment. A file in the human-owned aperture can remain unresolved until authorship or adoption is recognised. AIKit preserves that distinction through the resulting knowledge view.

A formal account and an ad hoc note both need a stable source reference and honest retrieval. Their richer interpretation differs. Markdown wikilinks and supported OKF metadata have a native relation compiler. This account’s HTML data attributes, seed hashes and resource registry require a deliberate integration contract before they can become equivalent structured Wiki staging input.

The sixfold is useful structure when the source supplies it. A plain file can enter as an ordinary source, and a meaningful partial whole can remain partial. The [[cap.aikit.wiki-shapes|QL shape service]] supplies valid structural readings while semantic edges continue to require actual evidence.

#4Where / When?

At the boundary of each act

design commitment

Carry common practice into particular work

A person’s baseline may include general research and editing practice. A Project can refine it with product terminology, relevant sources and selected capabilities. A session can further situate those choices around a current question.

The user should be able to inspect what came from each scope and change the appropriate source. Temporary requirements belong near the task that needs them. Shared improvements belong in the source that legitimately applies to future work.

[[cap.aikit.profiles|Profile composition]] and [[cap.aikit.methods|situated Methods]] support this development. The result is a practice that becomes more useful through experience while remaining understandable to someone entering the Project later.

architecture contract

Operate through the resources actually present

A working environment can include local or remote models, several harnesses, terminal multiplexers and specialised knowledge providers. Each provider exposes the operations it supports and the conditions under which they work.

The useful interface explains the present case. If a provider is missing, a known source may remain addressable with an unavailable retrieval route. If a harness supports only part of a composition, the reader needs to see the resulting limitation before relying on it.

Physical acceptance belongs to the actual arrangement exercised: provider version, host, target process and selected operation. The [[cap.aikit.models|model roster]] and [[cap.aikit.activation|activation receipt]] can preserve such observations. A successful core test establishes its own bounded behaviour, while a live provider claim needs its own observation.

temporal working state

The next documentation-to-Wiki integration

Authored Markdown reachability is now present: ordinary ProjectCentral notes retain source identity while their explicit links compile into the shared relation field. Bare notes remain authored sources rather than being promoted mechanically into Wiki nodes.

The immediate next step is durable, derived materialisation. Each root or project Wiki register needs its own content revision as the invalidation key before a local SQLite projection can replace eager rebuilding. Register and source refs remain owner-authored; no database row, path index or storage key may become semantic identity.

Search should then expose authored sources as a distinct hit kind alongside curated Wiki objects. Projection declarations can build on that provider-backed field as saved selections, while JSON remains canonical and the semantic rebuild remains the write-time validator.

The next integration should be reviewed against [[cap.aikit.authored-relations|source relations]], [[cap.aikit.knowledge-navigation|knowledge navigation]] and [[cap.aikit.wiki-write|write validation]] before any persistent projection is treated as ready.

#5Why-For?

A world that grows without overwhelming its actors

0/1 · Return to the seedExpanded account · review draft
vision

The practical return: a usable context

AIKit succeeds when a person or Agent can enter work, find the right resources, understand why they apply and use them through an appropriate environment. A wider collection should increase what can be done without making every new task harder to orient.

The result has several visible parts: discoverable powers, askable knowledge, understandable configuration, working provider bindings and a trace of what happened. Together they make the agentic environment something the person can deliberately develop.

Within O:I this is the connective operational role. Central gives intention a durable home. AIKit resolves the resources and information available for the current act. Actuation carries authorised agency, Factory develops the Project and Workcell supplies material conditions. The return can then improve the next source or method at its actual owner.
